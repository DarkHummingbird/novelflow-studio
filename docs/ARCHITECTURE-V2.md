# 架构方案 v2：从「本地工作台」到「可收费的 C 端续看服务」

> 目标：读者不填 Key、不登录也能先看到价值；收费后由服务端统一接入模型、记账、限流。
> 本文回答四个问题：前端怎么改、后端怎么建、要不要管理后台、模型配好后前端显示什么。

---

## 0. 一句话架构

```
        读者（手机/桌面浏览器）
              │  HTTPS + SSE
              ▼
   ┌──────────────────────────┐        ┌──────────────┐
   │  Reader SPA（本项目前端）  │───────▶│  API 服务     │──────▶ 模型厂商
   │  单页：粘贴 → 读          │        │  Node/Fastify │        (Key 只在这)
   └──────────────────────────┘        └──────┬───────┘
                                              │
                                    ┌─────────┴─────────┐
                                    │ SQLite / Postgres │  用户/订单/额度/用量/配置
                                    └─────────┬─────────┘
                                              │
                                    ┌─────────┴─────────┐
                                    │ Admin SPA（/admin）│  配模型、定价、看用量
                                    └───────────────────┘
```

**三个"只在服务端"**：模型 Key、额度账本、支付回调。
**前端只保留**：输入、流式阅读、本地草稿、登录态与余额展示。

---

## 1. 前端要改什么

### 1.1 两个入口，一个仓库

| 路由 | 内容 | 说明 |
| --- | --- | --- |
| `/` | **读者版**（新） | 默认入口，单列、移动优先 |
| `/studio` | 现有工作台 | 保留但不在读者版里露出，作为作者版/内测工具 |

同一套构建，`react-router` 或简单的 `pathname` 分流即可。读者版**不加载**工作台组件，包体还能降。

### 1.2 读者版页面结构

```
┌────────────────────────────┐
│ 剩余 3 篇 · 登录              │  ← 额度条（未登录显示"剩 1 篇免费"）
├────────────────────────────┤
│  把卡在收费处的小说贴进来     │
│  ┌──────────────────────┐  │
│  │                      │  │  ← 粘贴框（本地自动保存草稿）
│  └──────────────────────┘  │
│  后续大概：[短][中][长]      │  ← 三档对应 4,000/6,000/8,000 字
│      [ 读完这一本 ]          │  ← 主按钮（未登录先弹登录）
├────────────────────────────┤
│  正在写…… ▍                 │  ← 流式正文，边写边读
│  （正文）                    │
│  由 AI 生成 · 仅供参考        │  ← 合规标识
├────────────────────────────┤
│  [存到手机] [换一篇] [报错]   │
└────────────────────────────┘
```

### 1.3 要删的

- 「配置 API」弹窗、`ApiConfig` 类型、`localStorage` 存 Key 的逻辑；
- 读者版里的大纲编辑、项目/存档/备份、开发视图、检查面板；
- 所有把 provider/model 名字暴露给用户的文案（错误信息里也不能带）。

### 1.4 要加的

| 模块 | 说明 |
| --- | --- |
| `apiClient` | baseURL 改为 `/api`；带 `Authorization: Bearer <session>`；SSE 解析复用现有 `readSSE` |
| `useAuth` | 登录态、未登录先给 1 篇免费（本地指纹 + 服务端 IP 限次） |
| `useQuota` | 剩余篇数、超出单价、余额；生成完成后刷新 |
| 登录弹层 | 手机号+验证码（或内测期的邀请码） |
| 价格页 | 单篇 / 月卡 / 兑换码；标明"超出后 X 元/篇" |
| 错误映射 | 401→登录、402→额度不足、429→限流、5xx→"稍后重试，不扣次数" |

### 1.5 留在前端的

- 本地草稿（IndexedDB）——刷新不丢输入；
- 流式渲染、复制、导出 TXT、分享；
- 轻量埋点（可选，前端只记事件名，参数脱敏）。

## 2. 后端要建什么

### 2.1 技术选型（单人可维护优先）

| 项 | 建议 | 理由 |
| --- | --- | --- |
| 运行时 | Node 22 + Fastify | 现成 TS 能力可复用；SSE 简单 |
| 存储 | SQLite（better-sqlite3） | 单机即可，零运维；量大了再迁 Postgres |
| 校验 | zod | 入参/模型输出双向校验 |
| 部署 | 1 台 1C2G + Caddy（自动 HTTPS） | 不需要 K8s |
| 备选 | Cloudflare Workers + D1 | 免运维，但 SSE 与长任务不如 VPS 稳 |

### 2.2 表结构（7 张表起步）

```sql
users(id, phone, nickname, status, created_at)
sessions(token_hash, user_id, expires_at, ip, ua)
plans(id, name, price_cents, period_days, quota, overage_cents, active)
entitlements(id, user_id, plan_id, period_start, period_end, quota_total, quota_used, status)
orders(id, user_id, sku, amount_cents, channel, channel_txn, status, created_at)
generations(id, user_id, chars_in, chars_out, tokens_in, tokens_out, cost_cents,
            tier, status, gate_json, latency_ms, created_at)
settings(key, value_json, updated_at)          -- 模型配置、开关、公告
```

`settings` 里 `model_config` 一条就能让管理后台改完立即生效，不用发版。

### 2.3 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/auth/request-code` | 发验证码 |
| POST | `/api/auth/verify` | 换 session |
| GET | `/api/me` | 额度/套餐/是否需登录 |
| POST | `/api/generate` | **SSE**：`meta` → 增量正文 → `done{gate, usage}` |
| POST | `/api/generate/:id/cancel` | 中断 |
| GET | `/api/plans` | 价格与含篇数 |
| POST | `/api/orders` | 下单/兑换码 |
| POST | `/api/redeem` | 兑换码入账 |

### 2.4 生成链路（服务端）

```
校验 session → 检查额度 → 加并发锁（同账号同时 1 个）
  → 清洗用户文本（复用 core/text）
  → 选模型档位（服务端决定，不让前端指定）
  → 调模型（流式）→ 边收边转发给前端
  → 全文收完 → 跑五条检查（复用 core/gates）
      ├─ 通过 → 落库、扣 1 篇、返回 done
      └─ 不通过 → 服务端自动重写 1 次（不额外扣）→ 仍不通过则降级交付并记录
  → 释放并发锁
```

**扣费规则**（必须固定下来，否则客服会被问爆）：

- 成功且字数达到所选区间下沿的 80% 才扣；
- 失败 / 用户取消 / 5xx **不扣**；
- 服务端自动重试不扣；用户手动"重写一篇"扣 1 篇。

### 2.5 成本与滥用

- 单篇上限：输入 ≤ 8,000 字、输出 ≤ 9,000 字（服务端截断）；
- 单账号：并发 1、每日 50 篇、单 IP 每小时 20 次；
- 记录每篇 tokens 与估算成本，管理后台可按天看；
- 全局开关：一键停生成（模型故障或成本失控时）。

## 3. 要不要管理后台

**要。** 而且是这个产品的必需品，不是加分项。原因：

1. 模型要能**不发版就换**（换更便宜的模型、降级、临时关闭）；
2. 要能看到**今天花了多少钱、失败了多少**；
3. 出现失控（被刷）要能一键止损。

### 3.1 后台页面（一个 `/admin` 单页就够）

| 模块 | 内容 |
| --- | --- |
| 登录 | 密码 + TOTP（不要和用户同一套） |
| **模型配置** | 建"档位"：显示名 / provider / model / 单篇上限 / 温度 / maxTokens；测试连通性；设为默认；启停 |
| 定价 | 套餐 CRUD（含篇数、超出单价）、首篇免费开关 |
| 用户 | 搜索、额度调整、封禁、查看用量 |
| 订单 | 订单列表、兑换码生成与导出 |
| 观测 | 今日生成数、成功率、P50/P95 延迟、单篇成本、总成本、失败原因 Top5 |
| 内容 | 敏感词表、命中日志、抽样回看 |
| 开关 | 全局暂停、单档位停用、公告栏 |

### 3.2 Key 怎么存

- 首选 **环境变量**（`NF_PROVIDER_KEY`）；后台只读显示"已配置 · 末四位 XXXX"；
- 需要后台改的话，用 AES-GCM 加密后存 `settings`，主密钥放环境变量；
- 后台不提供"查看完整 Key"，只提供"替换"和"测试"。

## 4. 模型配好后，前端显示什么

这是最容易被忽略的产品决策：**前端不认识"厂商 + 型号"，只认识"档位"**。

| 后台配置 | 前端显示 |
| --- | --- |
| `fast` → deepseek-chat，显示名「极速版」 | 选择器里是「极速版」 |
| `std` → 更强模型，显示名「标准版」 | 「标准版」 |
| 全局状态：正常 | 不显示模型信息，只显示"剩余 3 篇" |
| 全局状态：降级 | 「当前为极速模式，生成更快」 |
| 模型故障 | 「服务繁忙，本次不扣次数」 |

**原因**：模型名对读者毫无意义，且换模型、换供应商、涨价降价都不该让用户感知；一旦把型号写进 UI，运营就被绑死了。

另外两处必须始终显示：**「由 AI 生成，仅供参考」**、**「剩余 N 篇」**。

## 5. 现有代码怎么迁移

| 现有文件 | 去向 |
| --- | --- |
| `src/lib/text.ts` / `gates.ts` / `router.ts` / `pipeline.ts` | 移到 `core/`，前端与后端共用 |
| `src/lib/api.ts` | 拆两半：**请求构造**进 `core/`，**Key 与 fetch** 留给后端 |
| `src/lib/idb.ts` / `archive` / `export` | 留在前端（读者版只保留草稿与导出） |
| `src/components/*`（工作台） | 全部留给 `/studio` |
| `scripts/proxy.mjs` | 废弃，能力并入后端 |

## 6. 分阶段落地

| 阶段 | 内容 | 工作量（单人） |
| --- | --- | --- |
| **P0 内测** | 后端骨架 + SSE 代理 + 邀请码/额度 + 读者版页面 | 2–3 天 |
| **P1 收费** | 手机号登录、套餐与超出计费、订单、后台模型配置与用量 | 4–6 天 |
| **P2 上线** | 正式支付（微信/支付宝）、监控告警、内容审核、退款流程 | 1–2 周 |
| **P3 优化** | 多模型路由与降级、A/B 定价、缓存与并发优化 | 持续 |

> 支付在 P1 可以先用**发卡平台卖兑换码**绕过商户号审核，等有量再上正式支付。

---

## 7. 风险与取舍

| 风险 | 应对 |
| --- | --- |
| 版权/平台规则 | 只做"用户主动提供文本"的工具；不提供书库、不做检索聚合；显著免责与退款政策 |
| Key 泄露 | 永不进前端；日志脱敏；定期轮换 |
| 被刷额度 | 服务端记账 + 并发锁 + 每日上限 + IP 限流 |
| 模型质量波动 | 档位抽象 + 快速换模型 + 失败不扣费 |
| 成本失控 | 单篇上限 + 每日成本看板 + 全局急停 |
| 单人维护负担 | SQLite 单机、无消息队列、无微服务 |
